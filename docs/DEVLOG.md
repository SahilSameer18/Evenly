- **Done (Part 2, backend B1 / Phase 2.1):** the expense create and read API. `POST/GET /households/:id/expenses` and `GET .../expenses/:expenseId`: shared (equal, exact, percentage, weighted), personal and on-behalf expenses; members, payer and category checks; the expense, splits and an audit event in one transaction; an `Idempotency-Key` (new `Expense.requestHash` column, migrated on dev and test) so a retry returns the stored result and a double tap makes exactly one expense; private personal expenses; filters and cursor pagination; ADR 004. - **Done (Part 2, backend B2 / Phase 2.2):** the expense lifecycle. Edit with optimistic locking (`PATCH` with the version; a stale one is `409 STALE_VERSION`), reverse (status change plus audit event, safe to repeat), partial refunds (new `refund` type with positive amounts, shared back pro rata, capped at the original even under simultaneous requests), disputes (reason in the audit trail, the disputer can withdraw, an edit resolves one), and `GET .../history`. Every change locks the expense row first and writes an audit event with before and after. Schema: `ExpenseType.refund` and `Expense.refundOfId` (migrated on dev and test). Ledger: refunds are subtracted. ADR 006, LEDGER.md status table. Decisions: creator-only edit and reverse; reverse by status, not a mirror row.
- **Done (test infrastructure, before B3):** the database tests were slow (575 s for 511 tests) and two simultaneous runs could wipe each other's data. Measured first: one query costs about 76 ms with any driver and a transaction about 400 ms, so the cost is round trips, not the driver. Added a run lock (a PostgreSQL advisory lock taken in a Vitest `globalSetup`; a second run is refused in about 3 seconds with a clear message, proven with a script holding the lock) and `makeWorld`, which builds a household and its members in one SQL statement (14 test files converted). Result: the two files timed before and after went from 130 s to 82 s, and the whole suite from 575 s to 421 s (516 tests) at the first full run with the changes. That run had one failure, an ordering assertion caused by the fixture using the database's clock while the app uses this computer's; fixed, and the affected files re-run (53 of 53), but I did not repeat the full suite. Removed the unused `@prisma/adapter-pg`; `pg` is now used by the lock. Larger gains would need parallel workers with separate schemas, left for later.
- **Done (Part 2, backend B3 / Phase 2.3):** settlements and balances. Repayments are recorded pending (idempotent) and only the recipient can confirm or reject, only the sender can cancel; each move locks the row and writes an audit event, repeating a move is a no-op, and a confirm racing a cancel has one winner. New `modules/balances` computes `GET /balances` (net plus paid, share, sent, received), `GET /ledger` (entries with every member's running balance) and `GET /settlement-suggestions` from the stored records through a new pure `explainLedger`. Create-expense, refund and confirm return `balanceAfter`; after money-changing writes the books are re-checked and a failure is logged with the request id, never failing the request. Leaving is blocked by a pending repayment. Schema: `Settlement.requestHash` and `resolvedAt` (migrated on dev and test). ADR 007. The worked example (+300 / -300) reproduces over HTTP.
